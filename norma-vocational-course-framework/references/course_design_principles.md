# 课程设计原则

## 课程总体结构

### 项目化设计

课程由若干"项目"组成，每个项目是一个完整的学习单元：

```
课程（64学时）
├── 项目一（8学时）— 岗位角色A的入门场景
├── 项目二（12学时）— 岗位角色B的进阶场景
├── 项目三（10学时）— 岗位角色C的专业场景
├── 项目四（12学时）— 岗位角色D的深入场景
├── 项目五（6学时）— 岗位角色E的综合场景
└── 项目六（16学时）— 岗位角色F的实战场景
```

### 课时分配原则

| 原则 | 说明 |
|------|------|
| 总学时64 | 职业本科课程标准学时 |
| 理论:实验 ≈ 3:7 | 强调实践，理论为实验服务 |
| 项目学时递进 | 入门项目学时少（8h），实战项目学时多（16h） |
| 综合实战占比最高 | 最后一个项目学时最多（16h），体现综合应用 |

### 每个项目的任务数

- 每个项目含2-3个任务
- 每个任务对应一个明确的工作任务
- 任务之间有递进关系（不是并列关系）

## 命名体系

### 项目命名：岗位场景命名法

**原则**：项目以岗位角色+场景描述命名，不以技术功能命名。

| 命名方式 | 示例（好） | 示例（差） | 区别 |
|----------|-----------|-----------|------|
| 岗位场景命名 | "嵌入式开发工程师入职上手" | "Linux基础" | 前者体现角色和场景 |
| 岗位场景命名 | "系统移植工程师构建部署" | "系统移植技术" | 前者体现角色和动作 |
| 岗位场景命名 | "工控产品工程师实战" | "综合实验" | 前者体现角色和应用领域 |

命名模板：`{岗位角色}{场景/动作描述}`

### 任务命名：工作任务命名法

**原则**：任务以具体的工作任务命名，体现可交付的工作成果。

命名模板：`{动词}{宾语}{补充说明}`

示例：
- "搭建Ubuntu开发环境与软件安装"
- "Linux命令行深入应用"
- "Shell脚本编程与自动化"

## 角色分离原则

### 设计理念

不同项目聚焦不同岗位角色，避免内容重叠：

```
项目一：XX工程师（使用者角色）— 学会使用系统
    ↓ 认知递进
项目二：XX工程师（开发者角色）— 学会在系统上开发
    ↓ 认知递进
项目三：XX工程师（专业角色）— 深入专业技能
    ↓ 认知递进
...
项目六：XX工程师（综合角色）— 综合实战应用
```

### 角色分离决策规则

| 判断维度 | 问题 | 决策 |
|----------|------|------|
| 认知层次 | 该内容属于"使用"还是"开发"？ | 使用→靠前项目，开发→靠后项目 |
| 依赖关系 | 该内容是否依赖其他内容？ | 被依赖的→靠前，依赖其他的→靠后 |
| 复杂度 | 该内容的复杂度如何？ | 简单→靠前，复杂→靠后 |
| 应用场景 | 该内容在哪个岗位角色中使用？ | 按角色归类到对应项目 |

## 验收标准体系

### 设计原则

**不使用时间标准**（如"20分钟内完成"），因为：
- 网络下载速度不可控
- 硬件性能差异大
- 编译时间取决于设备配置
- 时间标准不公平

### 五类验收标准

| 标准类型 | 定义 | 示例 |
|----------|------|------|
| **功能验证标准** | 操作产出的结果是否正确 | "QEMU成功启动，控制台输出Linux启动日志" |
| **质量规范标准** | 代码/操作是否满足质量要求 | "编译0 warning 0 error；shellcheck通过" |
| **过程完整性标准** | 是否完成全部必要步骤 | "完成全部7个工作步骤并产出中间结果" |
| **交付物标准** | 是否提交可验收的完整交付物 | "含Makefile+源码+README的完整工程" |
| **对比分析标准** | 虚拟与实物运行结果是否一致 | "QEMU与实物差异分析≥3点" |

### 每个技能点的验收标准格式

```
技能点：{技能名称}
操作要求：{具体操作描述}
验收标准：
  - 功能验证：{验证什么功能，预期结果}
  - 质量规范：{什么质量标准，如何检查}
  - 交付物：{提交什么，格式要求}
```

## 内容裁剪规则

### 裁剪原则

1. **有专门课程覆盖的内容→删除**：避免课程间内容重叠
2. **与课程定位不符的内容→删除**：聚焦核心方向
3. **过时技术→删除**：更新为当前主流技术
4. **新增内容需有政策依据**：如虚拟仿真（教育强国纲要数字化要求）、AI工具（人机协同设计）

### 裁剪决策流程

```
某内容是否纳入课程？
├── 是否有其他专门课程覆盖？
│   ├── 是 → 删除
│   └── 否 → 继续
├── 是否与课程核心方向一致？
│   ├── 否 → 删除
│   └── 是 → 继续
├── 是否在岗位实际工作中使用？
│   ├── 否 → 删除
│   └── 是 → 继续
├── 是否有政策要求？
│   ├── 是 → 纳入（标注政策依据）
│   └── 否 → 按学时空间决定
└── 纳入课程
```

## 虚拟仿真融入

### 三层定位

| 层次 | 定位 | 说明 |
|------|------|------|
| 教学空间层 | 虚拟课堂 | 降低硬件依赖，学生可在无开发板的情况下学习 |
| 开发流程层 | 先虚拟后实物 | 先在QEMU上验证，再部署到实物开发板 |
| 调试能力层 | 虚拟调试 | QEMU + GDB进行系统级调试 |

### 融入方式

- 项目一：不引入QEMU（先打好基础）
- 项目二：引入QEMU作为开发环境
- 项目三-五：QEMU + 实物双验证
- 项目六：以实物为主，QEMU为辅

## AI工具融入

### 融入原则

- 在适当项目中融入AI开发工具，落地"人机协同设计"政策要求
- AI工具作为辅助手段，不替代核心技能学习
- 放在有一定基础后的项目（通常项目二之后）
- 需考虑教学环境的算力限制，避免要求在虚拟机中运行大模型

### AI工具选型建议

| 工具 | 特点 | 适用场景 |
|------|------|----------|
| **Trae CN IDE** | 字节跳动AI原生IDE，免费，基于VSCode内核，Chat/Builder/智能补全三种模式 | 主力AI开发工具，代码生成、重构、调试 |
| **VS Code + Continue扩展** | 轻量方案，可接入DeepSeek等API或本地Ollama | 轻量级AI辅助，概念查询、代码解释 |
| **OpenClaw** | 开源MIT许可自托管AI网关，npm安装，支持多渠道交互 | 自建AI工具链，学习AI工具架构 |
| **Ollama** | 本地大模型运行框架 | 仅作简介，因虚拟机算力限制不要求实际运行 |

### 融入方式

- 作为开发工具使用（代码补全、错误诊断、代码审查）
- 作为学习工具使用（概念查询、代码解释、文档生成）
- 人机协同四原则：人工审查AI输出、理解AI建议再采纳、AI辅助而非替代、保持独立判断能力
- 不作为独立任务，融入现有任务的实战演练中

### 交付物要求

- AI工具配置文件（如 `ai_tool_config.md`）记录工具选型、配置方式、使用场景
- 不要求在虚拟机中运行Ollama等需要GPU算力的工具

## 实验项目对照表

### 设计目的

确保课程框架中的实验项目与教学项目/任务建立明确的对照关系，避免实验遗漏或重复。

### 对照表结构

```markdown
## 实验项目对照表

| 实验编号 | 实验名称 | 对应项目 | 对应任务 | 覆盖情况 | 备注 |
|----------|----------|----------|----------|----------|------|
| 实验1 | {名称} | 项目X | 任务Y | ✅ 已覆盖 | |
| 实验2 | {名称} | 项目X | 任务Y | ✅ 已覆盖 | |
| 实验3 | {名称} | 项目X | 任务Y（新增） | ✅ 已补充 | 原框架未含，已新增对应任务 |
| 实验4 | {名称} | — | — | ❌ 不纳入 | {不纳入原因} |
| 实验5 | {名称} | 项目X | 任务Y（新增） | ✅ 已补充 | |
```

### 对照原则

1. **逐实验分析**：每个实验检查是否已被框架中的项目/任务覆盖
2. **未覆盖处理**：对于未覆盖的实验，评估是否需要新增任务或标注不纳入及原因
3. **任务数调整**：新增实验对应的任务可能导致项目任务数变化，需同步调整学时分配
4. **学时总量不变**：新增任务时通过压缩其他任务学时保持总学时不变
