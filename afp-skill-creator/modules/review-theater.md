# 四审剧场（skill 开发版 · 本地轻量版）

> AFP Skill Creator · Module
> 触发：用户说 "审查一下" / "Review" / "我这 skill 有什么问题"——任意阶段可用
> 方法论来源：学君原创"四审剧场"（AFP Shared Primitive 候选：`afp-shared-review-theater`）。原版面向学术文本审查，本模块是其在 skill 开发场景的移植版

---

## 一、机制

四个独立评审角色依次上场，各自只从自己的立场挑毛病，**互不通气、不留情面**。四审结束后合成一份综合报告。

对象：用户当前正在创建的 skill（以已生成的 artifact 为准——SKILL.md、stages/、modules/、templates/、README）。

**纪律**：
- 每个评审只挑问题不给赞美（赞美不产生修改动作）
- 每条问题必须指到具体文件和位置，并给出修改建议
- 没生成的部分不审（标注"未生成，跳过"），不审空气

---

## 二、四位评审

### 审 1 · 架构评审（Committee 视角）

只看结构合规，逐项过：

- SKILL.md 是否薄路由（token 预算内、无业务细节下沉失败）
- stages/ 与 modules/ 边界是否正确（时序 vs 按需，见 stages/04 §六）
- 命名空间前缀 + frontmatter 五字段
- skill_type 与实际行为是否一致（最常见：写着 independent 干着 orchestrator 的活）
- Shared Primitive 复用机会是否被漏掉（自己造了已有 primitive 的轮子）

### 审 2 · 触发评审（生态邻居视角）

扮演"隔壁合伙人"，只看触发词会不会伤到别人或自己：

- 触发词覆盖是否够宽（用户找得到吗——变体口令测试）
- 是否太宽（抢了 orchestrator / 相邻 independent 的口令）
- 触发隔离段是否明确列出不触发场景
- 与 `~/.claude/skills/` 现有 skill 的 description 求交集，报潜在冲突

### 审 3 · 流程评审（AFP 步进纪律视角）

只看步进式六要素（stages/06 §二）的落实：

- 逐 stage 核对：单步输出边界声明 / Hard Stop 确认单 / "不允许自动推进"条款
- HUD 字段在各 stage 的更新是否闭环（有字段定义但从没人更新 = 死字段）
- 方案型决策点是否真的多方案
- 断点续传是否落实（状态文件格式 / 写入时机 / Continue 流程）
- 路由脚注链是否完整无断链

### 审 4 · 用户评审（小白视角）

扮演完全不懂方法论的目标用户，从首次触发话术开始通读：

- 首次引导看完知道该干嘛吗？
- 每个阶段的提问，目标用户答得出来吗？（要求用户提供他根本没有的东西 = 卡死点）
- 确认单看得懂吗？（内部术语未解释）
- 话术承诺的能力都有对应 stage 支撑吗？
- 走完全流程拿到的东西和当初被承诺的一致吗？

## 三、综合报告格式

```
╭─ 四审剧场 · 审查报告 ─────────────────────────────╮
│ 对象：{skill_name} · 审查范围：{已生成文件清单}
│ 
│ 🔴 必须修（阻塞上架）：{N} 条
│   1. [审X] {文件:位置} {问题} → {修改建议} → 回 P{N}
│ 🟡 建议修（影响体验）：{N} 条
│   1. [审X] …
│ ⚪ 可选（打磨项）：{N} 条
│ 
│ 📍 修复路由：🔴 全部清零前不建议进入 P7 生态集成
│ 👉 NEXT：逐条修复请说 "修第 1 条" / 全部采纳说 "全修" /
│         有异议逐条讨论
╰──────────────────────────────────────────────╯
```

分级标准：
- 🔴 **必须修**：违反 AFP-SPEC 条款、触发词冲突、流程断链、用户卡死点
- 🟡 **建议修**：token 超预算、话术生硬、确认单字段缺失
- ⚪ **可选**：措辞打磨、示例补充

---

## 四、使用时机建议

| 时机 | 审查重点 |
|---|---|
| P4 结构设计后 | 审 1 为主（结构还没写内容，改起来最便宜） |
| P6 每写完 2-3 个 stage | 审 3 + 审 4（趁早发现步进纪律漂移） |
| P7 生态集成前 | 全量四审（上架前最后一道关） |
| 用户迭代旧 skill 时 | 全量四审（作为迭代起点的诊断）|

---

## 五、反模式警告

- ❌ **审查变吹捧**：报告里一半篇幅夸优点——审查只为产生修改动作
- ❌ **问题不指位置**："触发词设计有问题"——必须指到文件、行、词
- ❌ **四审串通**：审 4 因为审 1 说结构好就放水——四个角色独立立场
- ❌ **报告不路由**：列了 20 条问题但不说回哪个 stage 修——问题清单变废纸
- ❌ **只在最后审一次**：P7 前才第一次审——结构性问题此时修改成本最高
