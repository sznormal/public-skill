# 薄路由 Pattern 指南

> AFP Skill Creator · Module
> 目的：解释 skill 主控为什么要薄 + 怎么写才算薄

---

## 一、核心原则

**主控 SKILL.md 应该在 1500-2500 token（约 3000-6000 字符）之间**。

不能超过 3000 token（约 8000 字符）。超过就是"厚主控"，违反 Anthropic Skills 的**渐进披露原则**。

---

## 二、Anthropic Skills 的加载机制

- 主控 SKILL.md **每次触发就完整加载**进入 context
- 详细模块（sub-md 文件）**只在用户明确需要时被 Read**——按需加载
- 用户可能不会用到全部功能，那些"未被 Read"的模块**不消耗 token**

**结论**：把内容放到子文档里，等于**延迟支付 token 成本**——用不到就不付。

---

## 三、薄主控的六个组成部分

一个 2000 token 的主控通常包含：

| 部分 | 用途 | token 预算 |
|------|------|-----------|
| 1 · Frontmatter | 系统识别 + 触发词 | 300-500 |
| 2 · 定位段（几句话） | 说 skill 是什么 | 100-200 |
| 3 · 核心设计理念（3-5 条） | 用户理解 skill 的判断依据 | 200-400 |
| 4 · 阶段路由表 | 各阶段名 + 加载哪个子文档 | 200-400 |
| 5 · 按需模块索引 | "用户说 X → Read Y" 表格 | 200-300 |
| 6 · 首次上手引导 | 触发后立即输出的 3 问 | 200-300 |
| 7 · 通用指令列表 | Next / Back / Skip 等 | 100-200 |
| **合计** | | **~1500-2500 token** |

---

## 四、什么内容"不应该"放在主控里

以下内容**必须**放到子文档，主控只保留索引：

- ❌ 具体阶段的执行细节（如"P3 文献综述阶段要做以下 5 步..."）
- ❌ 详细的方法论说明（如"温度调控原理详解"）
- ❌ 长篇的模板代码
- ❌ 详尽的示例
- ❌ 反模式清单（30+ 条）
- ❌ 审查规则详解
- ❌ 断点续传协议详情

**主控只需要"知道有这些能力"，不需要"当场展示这些能力"**。

---

## 五、什么内容"必须"在主控里

以下内容**必须**保留在主控（因为需要立即可用）：

- ✅ Frontmatter（触发词 + 描述）
- ✅ 一句话定位（用户 3 秒理解 skill 是什么）
- ✅ 触发词隔离规则（防冲突）
- ✅ 阶段路由表（决定接下来加载哪个子文档）
- ✅ 按需模块索引（决定哪些用户口令触发哪个模块）
- ✅ 首次上手引导（触发后立即引导用户）
- ✅ 通用指令表（Next / Back / Skip 等基础操作）
- ✅ 状态管理骨架（简短 JSON schema，200 token）

## 六、典型对比

### ❌ 反面案例（学君 V2 主控风格）

主控 32KB / 8000 token，包含：
- 完整的状态管理 JSON schema（500 行）
- 温度调控详细规则（12 阶段）
- 4 审剧场完整流程
- 考古发掘 5 层详解
- 莫比乌斯环精炼规则
- 30+ 反模式清单
- 12 章的完整业务逻辑

**每次触发一次性载入 8000 token**，用户可能只用到 20%，浪费 80%。

### ✅ 正面案例（AFP-skill-creator 主控）

主控 5917 字符 / ~2000 token，包含：
- Frontmatter + 触发词
- 5 条设计理念
- 状态骨架 JSON
- 9 阶段路由表（只列表格，不含细节）
- 按需模块索引表
- 首次上手引导
- 通用指令 + Hard Stop 输出规范
- 反模式警告（8 条精选，完整清单在子文档）

**每次触发只载入 ~2000 token**，其余按用户实际需求 Read。

---

## 七、"薄"和"简"不是同一件事

**薄 ≠ 简陋**。薄的主控可以承载复杂的能力，通过 Read 分层展开。

反例：主控 500 token，什么都没说 → 太简陋，用户不知道怎么用
正例：主控 2000 token，指路清晰 → 用户看完就知道怎么触发所有能力，具体细节在子文档

---

## 八、检查薄主控的 5 个自问题

写完主控 SKILL.md 后，问自己：

1. **删掉某段后，主控还能引导用户完成任务吗？**
   - 能 → 那段应该放子文档
   - 不能 → 保留在主控

2. **这段内容用户在什么场景才会用到？**
   - 每次都用 → 保留在主控
   - 偶尔用 → 放子文档，按需 Read

3. **这段内容用户能否用一句话触发？**
   - 能 → 放模块，用触发词加载
   - 不能 → 内嵌在主控

4. **这段内容和 Frontmatter 匹配吗？**
   - 触发词里说的功能都被主控覆盖吗？
   - 主控的功能都在触发词里体现吗？

5. **总 token 数在 2500 以下吗？**
   - 是 → OK
   - 否 → 找最长的段落，抽到子文档

---

## 九、薄主控的三个隐性好处

除了渐进披露 + 节省 token：

1. **可测试**：主控薄，逻辑清晰，容易测试和调试
2. **可协作**：主控是共识，子文档是分工——多人贡献时冲突小
3. **可演化**：明年 skill paradigm 变成 agent，薄主控更容易迁移

---

## 十、实践建议

写主控时的顺序：

1. 先写 Frontmatter（触发词）
2. 写状态骨架 JSON（HUD）
3. 写阶段路由表（架构骨架）
4. 写按需模块索引（能力索引）
5. 写首次上手引导（用户第一印象）
6. 写通用指令（操作 UX）
7. 用 wc -m 检查字符数 → 应该在 3000-8000 之间

**然后再详细写每个子文档 / 模块**——细节的家在那里。
