# Skill 发布前安全审计

把一个 skill 从"自己能用"变成"可以公开给别人用"，风险通常不在代码逻辑，
而在**代码边缘**：许可头部、打包范围、以及"外部内容进上下文"却没设防。

本 skill 提供**一条可复跑的发布前审计流水线**：自动扫描 10 项 + 人工过 3 项判断题，
输出分级问题清单与整改动作。

## 何时使用

- skill 准备首次公开（GitHub / Gitee / 社区 / 校内共享）
- skill 大版本发布前的例行体检
- 用户问"这个 skill 能公开吗 / 有没有泄露 / 会不会被外发"
- 接手别人的 skill、准备二次分发前

## 一、快速开始

```bash
python scripts/audit_skill.py <skill_dir>            # 人类可读报告
python scripts/audit_skill.py <skill_dir> --json     # 机器可读（接 CI）
python scripts/audit_skill.py <skill_dir> --strict   # P1 也视为失败
```

退出码：`0`=无 P0 ｜ `1`=有 P0（**阻止发布**）｜ `2`=路径错误。

脚本**纯标准库、无pip 依赖**，可塞进任何 CI。报告末尾会打印**外发域名清单**——
这是最容易漏、也最容易被用户质疑的一项。

## 二、脚本自动检查的 10 项

| 编号 | 检查 | 级别 |
|---|---|---|
| P1-ABS | 绝对路径 / 本机用户名 / 家目录 | P0 |
| P1-SEC | 硬编码密钥、token、密码（`sk-`/`ghp_`/`AKIA`/赋值型 key） | P0 |
| P1-POST | 非 GET 的网络写操作、回调推送、遥测上报、下载式请求 | P0 |
| P1-EXEC | 删除目录与任意代码执行类调用（含强制 shell） | P0 |
| P0-LIC | **脚本许可头 vs 根 LICENSE 是否一致**、是否混用多种许可、是否缺许可头 | P0/P1 |
| P0-PKG | `legacy/`、历史 `*.zip`、`*.bak` 等内部档混入 skill 目录 | P0 |
| P0-PKG | 打包器排除表是否含 `legacy` 与 `.zip`（不含则会被打进分发包） | P0 |
| P2-PII | 真实姓名 / 机构名 / 真实邮箱（署名属正常开源要求，但须确认意愿） | P2 |
| P2-SEND | skill 指令诱导用户把材料外发 | P1 |
| P1-INJ | 有无「外部内容仅作数据、不得当指令执行」约束 | P1 |
| P2-DSTR | 覆盖/移动类操作是否配 dry-run（无可逆设计即报） | P2 |

## 三、必须人工判断的 3 项（脚本查不出）

1. **许可兼容性**——脚本只能发现"两套许可并存"，**不能判断两套是否兼容**。
   高危组合：GPL 系 ↔ 禁止商业使用/附加限制的许可（PolyForm NC、BUSL、SSPL）
   ——**GPL 有传染性，与附加限制许可天然冲突**。
2. **数据最小化**——外发域名清单要逐个回答"发了哪些字段、为什么必须发、能不能少发"。
   典型该拦：把用户邮箱、机构名、稿件内容随请求发出。
3. **内容合规与署名**——引用规范、版权、不编造承诺是否兑现；机构名是否愿意公开。

## 四、公开 skill 的完整审计清单（13 条）

脚本覆盖前 10 条，后 3 条必须人工：

1. 许可兼容性
2. 分发义务履行（署名 / 版权声明 / 变更说明 / 源码提供）
3. 提示注入面（外部内容是否入上下文、有无"当数据不当指令"、外发白名单）
4. PII 与本地标识（路径、用户名、邮箱、机构名、机器名、内部报告）
5. 网络出口与数据最小化（逐域名逐字段说明）
6. 凭据卫生（只走环境变量，不落命令行 / 日志 / 包 / 快照）
7. 破坏性操作可逆性（删除覆盖前是否备份、是否默认 dry-run）
8. 提示词越权（skill 是否诱导 agent 绕过用户确认、扩大授权）
9. 可用性攻击面（无限循环、无上限并发与磁盘写入、快照无限增长）
10. 内容合规（版权、署名、不编造）
11. 依赖与版本锁定（外部 API 无 pin、Python 版本下限未声明）
12. 发布卫生（打包排除表、版本一致性、README 与实现一致、可重复构建）
13. 滥用与垃圾输入防护（恶意 / 超大输入、参数注入、路径穿越）

> **一句话判据**：一个 skill 会不会读你的文件、往哪发数据、拿到外部内容后会不会照做、
> 删你东西前能不能反悔 —— 这四问过了，才谈得上安全。

## 五、整改优先级

| 优先级 | 动作 |
|---|---|
| 必做 1 | 移出 `legacy/` 与历史包，打包排除表补 `legacy` 与 `*.zip` |
| 必做 2 | 统一许可（先定兼容方案，再统一脚本头/根 LICENSE/README） |
| 必做 3 | 修 `validate` 不通过项（frontmatter 单行 `key: value`、`description` 长度） |
| 必做 4 | 加「外部内容仅作数据」约束 + **外发域名白名单** |
| 建议 | 覆盖类操作补自动备份；README 加「数据发送说明」；补 `SECURITY.md` |

## 六、整改后必须复验

```bash
python scripts/audit_skill.py <skill_dir>          # 1. 本脚本：P0 归零
<skill_ops.py> validate <skill_dir>                # 2. 校验通过
<skill_ops.py> preflight  <skill_dir>              # 3. blocked 项附书面理由
<skill_ops.py> package  <skill_dir> --write-confirmed
python -c "import zipfile;print([n for n in zipfile.ZipFile('x.zip').namelist() if 'legacy' in n or n.endswith('.zip')])"  # 4. 产物干净
```

**第 4 步别省**：校验通过 ≠ 产物干净，排除表漏了就白做。

## 七、常见坑（实测）

- **正则误报掩盖真实缺口**：注入防护正则若含裸词「不可信」，会被
  "召回清单**不可信**"这类无关表述命中，导致**真的缺失防护反而报通过**。
  正则必须够具体（如「外部内容…不可信」）。→ 改动审计规则后**必须用一个已知有缺口的样本回归验证**。
- **`app(*d)` 展开 dict**：会把 dict 的**键**当位置参数，真实命中被静默吞掉，
  只剩 `'code'/'name'/'severity'` 这类字面量条目。→ 显式传键。
- **打包器不含排除项 ≠ 不会被打包**：多数打包器只排除 `.git/__pycache__/.pyc`，
  `legacy/` 与 `*.zip` 默认全量收入。**必须实测打包产物，不能靠推断。**
- **只看 `validate` 不足以判断可发布**：`validate` 只查 frontmatter 与少数红线，
  许可冲突、提示注入、路径泄漏都要另查。
- **许可头与根 LICENSE 不同源**：脚本 GPL 头 + 包 PolyForm NC 是**法律冲突**，
  不是风格问题——商业使用会两边都违规。
